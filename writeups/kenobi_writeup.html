Putting it all together: The Complete Kenobi Compromise

Executive Summary: To validate advanced manual exploitation techniques, I completed a complex boot-to-root engagement. This exercise required bypassing automated exploitation frameworks (e.g., Metasploit) to manually chain multiple service misconfigurations, exfiltrate protected credentials, and manipulate environment variables for root-level privilege escalation. Below is my complete A-Z methodology.

Step 1: Initial Reconnaissance (The Full Scope)

Point: Comprehensive Port Scanning
Reason: Before I can attack, I need to map every single open door on the target. Standard scans only check the top 1,000 doors. By running a full scan, I guarantee I don't miss obscure, high-number ports. I also need to know the versions of the software running behind those doors so I can look for specific weaknesses.
nmap -T4 -Pn -sS -sV -p- 10.48.187.114 -oN nmap_scan.txt
Execution Breakdown:
  • -T4: Aggressive speed so I aren't waiting all day.
  • -Pn: Assume the host is alive (bypasses firewalls blocking pings).
  • -sS: Stealth SYN scan to avoid full connection logging.
  • -sV: Probe open ports to determine exact service/version info.
  • -p-: Scan all 65,535 ports.
  • -oN: Save the output professionally to a text file.
The Link to Next Step: The scan results returned several targets, but Ports 139 and 445 (SMB/Samba) stood out. SMB is notorious for having misconfigured permissions, often allowing anonymous users to read internal company files. Because I saw SMB open, my immediate next move was to interrogate it.

Step 2: SMB Enumeration (Finding the Blueprint)

Point: Listing and Accessing SMB Shares
Reason: I know the SMB service is running, but I don't know what folders it is sharing. I need to ask the server for a list of shares, specifically checking if they allow "Null Sessions" (anonymous logins without a password).
1. smbclient -L //10.48.187.114/ -N > smb_shares.txt 2. smbclient //10.48.187.114/anonymous 3. smb: \> get log.txt 4. grep -i 'ftp' log.txt
Execution Breakdown: I first listed the shares and bypassed the password with -N, saving it to a text file. Seeing the anonymous share in my text file, I connected directly to it. I found and downloaded log.txt to my attack machine. Because the file was massive, I parsed it using grep -i 'ftp' log.txt.
The Link to Next Step: My grep command revealed FTP is running on Port 21. Furthermore, reading the rest of the log revealed that the user kenobi has an SSH private key located in a highly restricted folder: /home/kenobi/.ssh/id_rsa. I want that key. But I cannot reach the /home/kenobi/ folder from the outside. I need to find a public folder on the machine where I can reach things. I remembered Port 111 (RPC) was open in my initial Nmap scan, which manages Network File Systems (NFS). Let's see if NFS is sharing a public folder.

Step 3: NFS Enumeration (Finding the Public Lobby)

Point: Discovering Network Mounts
Reason: NFS allows a server to expose physical folders on its hard drive to the rest of the network. I need to ask the RPCbind service on Port 111 exactly which folders are exposed. I am looking for a "public lobby" where I can eventually drop the stolen SSH key.
nmap -p 111 --script=nfs-showmount 10.48.187.114
The Link to Next Step: The output showed that the /var directory is shared publicly. The Strategy: I have a locked key (/home/kenobi/.ssh/id_rsa) and a public lobby (/var). I need a mechanism to transport the key from the locked room to the lobby. I remembered ProFTPd is running on Port 21. If that FTP software has a vulnerability, I might be able to force it to move the file for me.

Step 4: FTP Exploitation (The File Heist)

Point: Weaponizing ProFTPd mod_copy
Reason: First, I grab the exact version of the FTP software using Netcat (nc 10.48.187.114 21), which reveals ProFTPd 1.3.5. I use searchsploit proftpd 1.3.5 and discover the mod_copy vulnerability. This flaw allows an attacker, without even logging in, to issue commands to copy any file on the system to any other directory.
1. nc 10.48.187.114 21 2. SITE CPFR /home/kenobi/.ssh/id_rsa 3. SITE CPTO /var/tmp/id_rsa
The Link to Next Step: The exploit was successful. Kenobi's private SSH key is now sitting in /var/tmp/id_rsa. Because I discovered in Step 3 that /var is a public network share, I can now simply connect my computer to that share, grab the key, and use it to log in.

Step 5: Gaining Initial Access (The Break-In)

Point: Mounting the Share & Bypassing Passwords
Reason: I cannot just download the key through a browser. I must formally "mount" the target's /var directory to my own attack machine's file system, making it look like a local hard drive. Once I copy the key, I must restrict its permissions (chmod 600), because the SSH protocol is designed to reject private keys that are too easily readable by other users.
1. mkdir /mnt/kenobiNFS 2. mount 10.48.187.114:/var /mnt/kenobiNFS 3. cp /mnt/kenobiNFS/tmp/id_rsa . 4. chmod 600 id_rsa 5. ssh -i id_rsa kenobi@10.48.187.114
The Link to Next Step: I am finally inside the machine! But I am just the user kenobi. I don't have ultimate control. To take over the whole machine, I need to find a way to become the root user. The best way to do this in Linux is to find poorly configured administrator programs (SUID binaries).

Step 6: Privilege Escalation Recon (Hunting SUIDs)

Point: Locating Vulnerable SUID Binaries
Reason: SUID (Set Owner User ID) is a special permission. If a file has this enabled, it executes with the permissions of the person who created it, not the person running it. If root created the program, anyone running it temporarily gains root privileges. I need to find all SUID files and look for one that shouldn't be there.
find / -perm -u=s -type f 2>/dev/null
The Link to Next Step: The find command reveals a highly unusual custom program: /usr/bin/menu. When I run it, it gives me a 3-option menu. By using the strings command on the file, I discovered that Option 1 runs the curl command. However, the programmer made a mistake: they didn't write /usr/bin/curl (the strict path). They just wrote curl. This means I can trick the system into running my version of curl.

Step 7: The Root Exploit (Path Hijacking)

Point: Manipulating the $PATH Environment Variable
Reason: When a program just asks for curl, Linux checks the $PATH—a predefined list of folders—to figure out where curl is located. It checks the first folder, then the second, until it finds a match. My goal is to create a malicious file, name it curl, and edit the $PATH list to put my folder at the very front. When /usr/bin/menu runs, Linux checks my folder first, finds my fake curl, and executes it. Because /usr/bin/menu has the SUID permission, my fake curl gets executed with absolute root privileges.
1. cd /tmp 2. echo /bin/sh > curl 3. chmod 777 curl 4. export PATH=/tmp:$PATH 5. /usr/bin/menu
The Link to the End: Option 1 triggers my fake curl. A root shell spawns. I type whoami and verify I am root. I read /root/root.txt, capture the final flag, and the machine is fully compromised.
