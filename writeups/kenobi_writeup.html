The Kenobi Compromise: Detailed Blueprint

Step 1: Initial Reconnaissance

Point: Comprehensive Port Scanning
nmap -T4 -Pn -sS -sV -p- 10.48.187.114 -oN nmap_scan.txt
Execution Breakdown:
  • -T4: Aggressive speed so the scan runs faster.
  • -Pn: Assumes the host is alive, bypassing firewalls that block pings.
  • -sS: Stealth SYN scan to avoid leaving a full connection log on the target.
  • -sV: Probes the open ports to find the exact software version running.
  • -p-: Scans all 65,535 ports to guarantee nothing is missed.
  • -oN: Saves the output to a text file for professional reporting.
The Result: I found SMB (Ports 139/445), FTP (Port 21), and RPC (Port 111) open.

Step 2: SMB Enumeration

Point: Listing and Accessing SMB Shares
1. smbclient -L //10.48.187.114/ -N > smb_shares.txt 2. smbclient //10.48.187.114/anonymous 3. smb: \> get log.txt 4. grep -i 'ftp' log.txt
Reason & Execution: I first used the -L flag and -N (no password) to ask the server for a list of shares. I saw a folder named 'anonymous'. I logged into it and downloaded log.txt. Because the file was huge, I used grep to filter for the word 'ftp'.

Crucial Discovery: The log revealed Kenobi has a private SSH key hidden in a locked folder: /home/kenobi/.ssh/id_rsa.

Step 3: NFS Enumeration

Point: Discovering Network Mounts

Reason & Execution: I want Kenobi's locked SSH key, but I can't reach it from the outside. I remembered Port 111 (RPC) was open. RPC manages Network File Systems (NFS). I used a specific Nmap script to ask the server what folders it shares publicly. It revealed the /var directory is exposed. I now have a "public lobby" to use.

Step 4: FTP Exploitation

Point: Weaponizing ProFTPd mod_copy

Reason & Execution: I connected to Port 21 with Netcat (nc) and saw ProFTPd version 1.3.5. Using searchsploit, I found the mod_copy vulnerability. This bug lets me copy files without logging in. I commanded the server to copy the locked SSH key (CPFR - Copy From) and drop it into the public /var/tmp lobby (CPTO - Copy To) that I found in Step 3.

Step 5: Gaining Initial Access

Point: Mounting the Share & Bypassing Passwords

Critical Step: I used chmod 600 to lock the key's permissions. If I don't do this, the SSH protocol will reject the key for being "too openly readable" by others. Finally, I logged in as Kenobi using the key (-i) instead of a password.

Step 6: Privilege Escalation Recon

Point: Locating Vulnerable SUID Binaries
find / -perm -u=s -type f 2>/dev/null strings /usr/bin/menu
Reason & Execution: I am inside, but I need 'root' (admin) powers. I used the find command to locate SUID binaries—programs that temporarily grant the user root privileges when run. I found a weird custom program called /usr/bin/menu. Because it is compiled code, I used the strings command to extract the human-readable text hidden inside it. I saw that the program tries to run the curl command, but it fails to specify the exact, absolute path (like /usr/bin/curl).

Step 7: The Root Exploit

Point: Manipulating the $PATH Environment Variable

Reason & Execution: Because the menu program doesn't know exactly where curl is, it checks the Linux $PATH variable (a list of folders) to find it.

I went to the /tmp folder and created a fake file named curl containing the command to spawn a root shell (/bin/sh). I made it executable (chmod 777). Then, I hijacked the system by changing the $PATH list, forcing Linux to check my /tmp folder first.

When I ran the menu program, it looked for curl, found my fake file first, and executed it. Because menu has SUID permissions, my fake file executed with absolute root privileges. The machine is fully compromised.
